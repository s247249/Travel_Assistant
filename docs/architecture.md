# Architecture & Decision Log — Travel RAG Assistant

Status: **design phase** (pre-implementation). This document is maintained incrementally:
every significant choice is recorded with its alternatives and rationale.

## 1. Objective

Conversational virtual assistant for travel & experiences: collects user requirements
(budget, nation, activity preferences, travel month) via chat, generates complete
constraint-respecting itineraries (flights + hotel per night + daily activities),
and supports booking with persisted status. See project guidelines for full spec.

## 2. Core architectural principle: two knowledge stores

| | Semantic knowledge | Hard facts & constraints |
|---|---|---|
| Examples | activity descriptions, ideal targets (families, young, sporty) | prices, dates, availability, bookings |
| Store | Vector DB (Chroma) | Relational DB (SQLite) |
| Query style | embedding similarity + metadata filters | exact SQL |
| Used for | preference matching, recommendations, explanations | budget math, availability checks, booking |

**Golden rule:** the LLM converses and orchestrates; deterministic Python code computes.
Budget arithmetic, availability checks and booking commits never rely on the LLM.
Both stores share entity IDs (e.g. `activity_barcelona_007`), so a semantically
retrieved activity maps directly to its bookable SQL record.

```
User ⇄ Chat UI ⇄ FastAPI ⇄ LangGraph agent (Gemini)
                              ├─ tool → Retriever → Chroma (descriptions, targets)
                              ├─ tools → SQLite (flights/hotels search, budget check)
                              ├─ tool  → Itinerary builder (plain Python, constraint-checked)
                              └─ tool  → Booking service (writes Bookings, requires user confirmation)
```

7. **Frontend** — chat, itinerary visualization, bookings dashboard
8. **Deliverable polish** — README, architecture notes, git history

## 5. Known simplifications (to document honestly in README)

- Synthetic inventory, not live travel data; booking is simulated against local DB.
- Some routes operate only a few days per week (intentional, to exercise constraint handling).
- One representative airport per city (Milan = MXP only); no self-flights — origin = destination is handled conversationally.
- Hotel names are fictional; activity names reference real landmarks/experiences, but prices and availability are synthetic.
- Cancellation: whole booking, any time, no fees; item-level editing parked (to be re-discussed, D25/B3).
- Chat booking consent is LLM-mediated (preview-by-default + explicit flag mitigate); Phase 7 adds a code-only button path.

## 7. Data generation pipeline (Phase 1)

```
scripts/generate_inventory.py  (deterministic, seeded, stdlib only)
    ├─→ db/travel.db            (SQLite: airports, cities, hotels+availability,
    │                            activities+availability, flights; gitignored, regenerable)
    └─→ data/inventory.json     (static entities + IDs + base prices; committed)
            │
scripts/make_corpus_prompt.py --city <id>
    └─→ data/prompts/<city>_prompt.md   (entity list embedded; committed)
            │  user runs prompt in a separate LLM chat
            ▼
    data/corpus_raw/<city>.txt          (raw chat output, === FILE: ... === separators)
            │  scripts/validate_corpus.py (split + normalize/repair + validate; writes data/corpus/<city>/)
            ▼
    data/corpus/<city>/*.md             (validated Markdown; committed)
            │  scripts/ingest_corpus.py (fit-or-split → Gemini embeddings → Chroma)
            ▼
    db/chroma/                          (gitignored, regenerable)

data/eval/queries_raw.json → validate_eval.py → queries.json → eval_retrieval.py → results.json
```

- Regenerating with more months (D7): `--months 2026-06 ... 2026-10`.
- Anti-drift contract: no exact prices/hours/availability in corpus prose; shared IDs join Chroma ↔ SQLite.

## 8. Ways of working: manager + delegation

- **Explanation standard (user requirement):** every artifact the manager writes gets a
  complete explanation — purpose, inputs/outputs, what each part does and why — not
  line-by-line, but no hand-waving. The user must be able to explain every file themselves.

- **Manager (this chat):** design discussion with the user, schemas/contracts, core code
  (agent, booking, API), validation, integration. Anything requiring cross-component
  consistency stays here.
- **Delegated subwork (user's other LLM sessions):** bulk content generation, executed via
  precise prompts written by the manager (`data/prompts/`). Two modes:
  - *Agent mode* (pi in a terminal, from project root):
    `pi --print "@data/prompts/<city>_prompt.md Execute this task exactly as specified."`
    — the agent writes `data/corpus_raw/<city>.txt` itself (write tool only; no copying).
  - *Chat UI mode*: user copies raw output (code-fence copy button) to `data/corpus_raw/<city>.txt`.
  In both cases the manager splits and validates against the contract before anything
  enters `data/corpus/`.
- **Delegation criteria:** bulk/content-heavy, separable by a strict contract, low need
  for whole-project context. The manager proactively notifies the user whenever a task
  qualifies ("delegation notice" with prompt path + where to save output).
- **Delegation queue:**
  1. Corpus generation — **DONE, all 6 cities**: 114/114 documents validated (`data/corpus/`).
     Rome: rendered-copy artifacts auto-repaired. Barcelona: 8× `families`→`family` alias
     normalization (validator alias map). Paris/Rome: minor word-count overshoots accepted.
  2. Retrieval eval set (P5/D18) — **DONE**: 18 queries validated, scored 100% hit@5/hit@1,
     MRR 1.000 (`data/eval/results.json`); caveats recorded in D18.
  3. Candidate (decide when reached): frontend copy/static mockups (Phase 7).

**Phase 4 verification notes (honest record):** 7/7 deterministic planner tests (0 API calls),
constraints re-verified against the DB; end-to-end chat loop verified (requirements → build →
objection → pin rebuild). The live test caught two real issues: (a) pins keyed by date could be
silently sidestepped when the optimizer chose a window not containing the pin date — fixed:
pins now constrain window selection before truncation, regression tests 6–7; (b) the model
narrated a swap that was not in the tool result (narrative drift) — mitigated by prompt rule
"copy exactly from the tool summary"; structural fix in Phase 7: the UI renders proposals from
state, the LLM only comments. Both incidents validate architecture A: verify guarantees in code,
never trust the narrative.
